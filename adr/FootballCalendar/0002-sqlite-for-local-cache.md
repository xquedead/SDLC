# ADR-0002: Использование встроенной СУБД SQLite для локального кэша и пользовательских данных

## Контекст и постановка задачи

Согласно бизнес-цели `BG-4` и требованиям `REQ-FUNC-013`, `REQ-AVAIL-001`, приложение «Футбольный календарь» должно обеспечивать просмотр расписания, карточек матчей, турнирных таблиц, списка бомбардиров и избранных команд без подключения к интернету по последним загруженным данным. Кроме того, требование производительности `REQ-PERF-001` устанавливает, что открытие календаря из кэша объёмом до 2000 матчей должно занимать не более 1 секунды на ПК с 4 ГБ ОЗУ, а требование надёжности `REQ-REL-002` требует автоматического пересоздания повреждённого файла кэша без аварийного завершения приложения.

Необходимо выбрать механизм локального хранения кэша матчей, списка избранных команд (до 20 клубов, `REQ-FUNC-008`) и расписания напоминаний (`REQ-FUNC-009`).

## Драйверы решения

* Ограничение продукта `C-4`: для хранения кэша должна использоваться встроенная СУБД SQLite (через модуль `Qt 6 Sql`, `C-1`).
* Требование производительности `REQ-PERF-001`: загрузка до 2000 матчей из кэша не более чем за 1 с и фильтрация по турнирам/датам/подстроке названия команды (`REQ-FUNC-001`…`003`).
* Требование надёжности `REQ-REL-002`: целостность данных при сбоях и автоматическое восстановление схемы при повреждении файла кэша.
* Ограничение памяти `REQ-PERF-003`: потребление ОЗУ не более 200 МБ.

## Рассмотренные варианты

* **Вариант 1:** Встроенная реляционная СУБД **SQLite** (драйвер `QSQLITE` из состава `Qt 6 Sql`) с нормализованной схемой таблиц, индексами по дате и турниру и транзакционной перезаписью кэша.
* **Вариант 2:** Хранение необработанных JSON-ответов API в отдельных текстовых файлах на диске с полным парсингом в оперативную память при запуске.
* **Вариант 3:** Хранение всех данных в системном реестре или INI-файлах через `QSettings`.

## Итог решения

Выбранный вариант: **«Вариант 1: Встроенная реляционная СУБД SQLite с транзакционным обновлением и проверкой целостности `PRAGMA quick_check`»**, потому что он выполняет обязательное ограничение `C-4`, обеспечивает выборку и фильтрацию 2000 матчей за десятки миллисекунд (запас по `REQ-PERF-001`), поддерживает атомарные транзакции (старый кэш не теряется при обрыве сети по `REQ-REL-001`) и позволяет легко обнаружить повреждение файла БД и пересоздать схему по `REQ-REL-002`.

### Последствия

* Хорошо, потому что SQL-запросы с индексами `idx_matches_date` и `idx_matches_comp` позволяют мгновенно фильтровать матчи по периоду (день/неделя/месяц), турнирам и поиску команды без загрузки всех записей в память (`REQ-PERF-003`).
* Хорошо, потому что транзакция `BEGIN IMMEDIATE ... COMMIT` гарантирует, что при ошибке сети или сбое питания ранее загруженные данные остаются целыми (`REQ-REL-001`).
* Нейтрально, потому что пользовательские настройки (токен API, язык интерфейса, часовой пояс — `REQ-FUNC-014`, `REQ-SEC-002`) хранятся отдельно от файла кэша в профиле пользователя Windows, поэтому пересоздание повреждённого файла `cache.db` (`REQ-REL-002`) не сбрасывает API-токен.
* Плохо, потому что требуется проектирование схемы из 7 таблиц и написание SQL-миграций при обновлении структуры.

### Подтверждение

1. Автоматический тест `REQ-PERF-001`: заполнение базы 2000 тестовыми матчами и замер времени выборки недельного расписания (критерий: `<= 1000 мс`).
2. Автоматический тест `REQ-REL-002`: запись случайных байтов в файл `cache.db` перед запуском — приложение должно выполнить `PRAGMA quick_check`, обнаружить ошибку `SQLITE_CORRUPT`, пересоздать файл `cache.db` и показать информационное сообщение пользователю без падения процесса.

## Плюсы и минусы вариантов

### Вариант 1: Встроенная СУБД SQLite (`QSQLITE`)

* Хорошо, потому что полностью соответствует `C-1`, `C-4`, `REQ-PERF-001`, `REQ-FUNC-008`, `REQ-REL-002`.
* Хорошо, потому что не требует установки отдельного сервера БД (`SRS 3.5.1`).
* Плохо, потому что требует аккуратного обращения с соединениями между потоками в Qt.

### Вариант 2: Текстовые JSON-файлы на диске

* Хорошо, потому что позволяет сохранять ответы API без преобразования.
* Плохо, потому что нарушает ограничение `C-4` (обязательное использование SQLite).
* Плохо, потому что при фильтрации 2000 матчей и поиске пересечений (`REQ-FUNC-011`) требует полного разбора всех JSON-файлов в ОЗУ.

### Вариант 3: Хранение в `QSettings` (реестр / INI)

* Хорошо, потому что подходит для 3–4 простых параметров настроек (`REQ-FUNC-014`).
* Плохо, потому что абсолютно непригодно для хранения 2000 матчей, таблиц и бомбардиров.

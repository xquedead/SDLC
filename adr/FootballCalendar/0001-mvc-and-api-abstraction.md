# ADR-0001: Применение архитектуры MVC и изоляция внешнего источника данных за интерфейсом `IFootballApiClient`

## Контекст и постановка задачи

Приложение «Футбольный календарь» (`FootballCalendar`) является desktop-приложением на C++17 и Qt 6 (`C-1`, `C-2`), которое получает данные о турнирах, матчах, турнирных таблицах и бомбардирах из внешнего веб-сервиса `football-data.org` REST API v4 (`C-3`, `REQ-INT-002`) и отображает их на четырёх экранах (`UI-01`…`UI-04`, `REQ-INT-001`). Согласно разделу `2.5` и пункту `3.5.4` спецификации требований (`SRS`), внешний сервис может изменить формат ответов или тарифные ограничения, а само приложение должно поддерживать автономный режим работы из локального кэша (`REQ-FUNC-013`, `REQ-AVAIL-001`) и модульное тестирование (`Раздел 4 SRS`).

Необходимо определить архитектурный стиль организации кода и способ сопряжения прикладной логики с внешним сетевым источником данных: как разделить представление, бизнес-логику и доступ к данным, чтобы изменения в `football-data.org` API v4 не приводили к переписыванию экранов Qt и алгоритмов расчёта пересечений матчей?

## Драйверы решения

* Требование сопровождаемости (`SRS 3.5.4`): разделение на модель, представление и контроллер и изоляция модуля доступа к API интерфейсом.
* Ограничение единственного источника данных (`C-3`, `REQ-INT-002`) и риск изменения внешнего API (`SRS 2.5`).
* Необходимость автоматического модульного тестирования API-клиента и бизнес-логики без реальных сетевых вызовов (`SRS Раздел 4`, верификация `REQ-INT-002`, `REQ-FUNC-011`, `REQ-FUNC-012`).
* Работа в автономном режиме с прозрачным переключением между сетью и локальным кэшем SQLite (`REQ-FUNC-013`, `REQ-AVAIL-001`).

## Рассмотренные варианты

* **Вариант 1:** Слоистая архитектура **MVC (Model–View–Controller)** с выделением абстрактного интерфейса `IFootballApiClient` (паттерн *Adapter / Strategy*) и репозитория `ICacheRepository`.
* **Вариант 2:** Монолитная организация логики внутри классов окон Qt (`MainWindow`, `MatchCardDialog`) с прямыми вызовами `QNetworkAccessManager` и SQL-запросов из обработчиков кнопок (*Smart UI*).
* **Вариант 3:** Архитектура **MVVM** на базе Qt Quick / QML с двусторонним связыванием свойств.

## Итог решения

Выбранный вариант: **«Вариант 1: Слоистая архитектура MVC с выделением интерфейса `IFootballApiClient` и репозитория `ICacheRepository`»**, потому что он напрямую выполняет требование `SRS 3.5.4`, соответствует ограничению `C-1` (использование модуля `Qt 6 Widgets`), позволяет подменять реальный сетевой клиент `FootballDataApiClient` тестовым двойником (*Mock/Stub*) при проверке `REQ-INT-002` и `REQ-REL-001`, а также изолирует экраны `UI-01`…`UI-04` от формата JSON внешнего сервиса.

### Последствия

* Хорошо, потому что при изменении формата `football-data.org` API или переходе на другой источник данных потребуется модифицировать только класс `FootballDataApiClient`, не затрагивая `MainWindow`, `CalendarController` и `SqliteCacheRepository`.
* Хорошо, потому что контроллеры и доменные сервисы (`SyncService`, `ConflictDetector`, `FavoritesService`) тестируются изолированно без доступа в интернет.
* Плохо, потому что увеличивается начальное число классов и интерфейсов (необходимость описания DTO-структур и чистых виртуальных классов `IFootballApiClient`, `ICacheRepository`).

### Подтверждение

Соблюдение решения проверяется при инспекции кода (*Inspection*) и модульном тестировании (*Test*):
1. Классы представления (`MainWindow`, `MatchCardDialog`, `StandingsWidget`, `MyCalendarWidget`) не содержат заголовков `<QNetworkAccessManager>` и `<QSqlQuery>`.
2. Модульный тест API-клиента и сервиса синхронизации (`SRS Раздел 4`, `REQ-INT-002`) выполняется с использованием mock-реализации `IFootballApiClient`.

## Плюсы и минусы вариантов

### Вариант 1: MVC + интерфейс `IFootballApiClient` и `ICacheRepository`

* Хорошо, потому что обеспечивает низкую связность (*low coupling*) и прямое соответствие пункту `3.5.4 SRS`.
* Хорошо, потому что упрощает параллельную работу с `junior`-разработчиком (чёткие контракты между UI и логикой).
* Плохо, потому что требует написания адаптеров преобразования JSON в доменные модели.

### Вариант 2: Логика внутри классов окон Qt (*Smart UI*)

* Хорошо, потому что быстрее пишется на самых первых часах разработки прототипа.
* Плохо, потому что нарушает `SRS 3.5.4` и делает невозможным автоматическое тестирование без запуска графического окна.
* Плохо, потому что любое изменение API ломает код всех четырёх экранов.

### Вариант 3: MVVM на базе Qt Quick / QML

* Хорошо, потому что поддерживает декларативное описание интерфейса.
* Плохо, потому что противоречит ограничению `C-1` спецификации (`Qt 6: модули Widgets, Network, Sql`) и требует изучения стека QML.
